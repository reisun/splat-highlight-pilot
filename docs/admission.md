# 受付の排他制御と復旧記録

`app/admission.py` の `AdmissionController` は、指定ディレクトリの
`admission.lock` を Linux の `flock` で排他取得する。
取得は待機せず、他の処理が保持している場合は `False` を返す。
同じインスタンスからの二度目の取得も拒否する。
ロックファイルは削除しない。削除して再作成すると別の inode に対する
ロックができ、二重受付が成立するためである。

## インターフェース

| 操作 | 動作 |
|---|---|
| `try_acquire()` | 待機せず取得。既存の処理記録は上書きしない |
| `snapshot()` | 所有権に関係なく記録を取得。記録なしは `None` |
| `update(**fields)` | ロック保持時のみ既存記録に項目を追加・更新 |
| `release(clear=True)` | 記録削除を永続化してから保持するロックを閉じる |
| `release(clear=False)` / `close()` | 記録を残してロックを閉じる |
| `lock_fd` | 管理する FFmpeg に `pass_fds` で継承できる FD |
| `is_locked()` | 別 FD で非待機の取得を試し、他プロセス・子を含む所有状況を確認 |

処理記録 `admission.json` の項目は呼び出し元で定義する。例えば
`phase`、`received_bytes`、`total_bytes`、`backend_job_id`、`backend_kind`、
`progress`、`estimated_finish_at` を保存する。更新時には UTC の
`updated_at` を追加する。記録の読み書きは同一インスタンス内の
`RLock` で保護し、一時ファイルの `fsync`、atomic replace、
ディレクトリの `fsync` で公開する。他プロセスには更新前か更新後の
完全な JSON が見える。

## 中断と再起動

ロックは FD が閉じると解放される。FFmpeg に FD を継承した場合は、
受付サービスが終了しても FFmpeg が生存している間はロックが残る。
このため解放時に明示的な `LOCK_UN` は実行せず、FD を閉じる。

ロック取得成功だけでは別サービスの解析終了を保証できない。
呼び出し元は既存の処理記録と analyzer の実行状態、管理下の変換処理を
照合してから新規受付を許可する。照合不能の記録は残して受付を閉じる。
一定時間経過や推定終了時間だけを理由に解放しない。
記録が壊れている場合は `AdmissionStateError` として受付を拒否する。

通常終了時は結果保存・後片付け完了後に `release()` を呼ぶ。
結果が不明な終了時やサービス停止時は `close()` で復旧記録を残す。
ロックの所有者でないインスタンスからの `release()` は記録を削除しない。

## 検証

`tests/test_admission.py` で複数コントローラーの排他、プロセス終了、
子プロセスへの FD 継承、破損した記録の拒否、書き込み失敗時の原記録保持、
並列読み出しで完全な JSON が見えることを検証する。
ロックは同じローカルファイルシステムを共有する Linux プロセス向けであり、
複数ホスト間の分散ロックとしては使用しない。
